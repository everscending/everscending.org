## 3. What went well

- **Scope respected:** Story 1.1 stayed as a shell-only blog section (semantic section, heading, loading state). No scope creep into API or real posts; clear handoff to Epic 2.
- **Alignment with architecture:** BlogSection used existing layout (`outer-container`, `inner-container`), App.css variables, and co-located CSS. No new design system or global layout changes.
- **Performance (NFR-P1):** Shell and nav render first; blog section does not block initial paint; in-section loading only.
- **Accessibility baseline:** Semantic `<section aria-label="Blog">`, `<h2>Blog</h2>`, and focus styling (accent-orange/yellow) per UX/architecture.
- **Test coverage:** New component tests and E2E for blog section on home; App tests updated to match current nav and blog presence.
- **Code review used:** Review confirmed ACs and tasks done, updated file list, and explicitly recorded the decision to proceed without fixing remaining Medium/Low items (product owner discretion).

---

## 4. Challenges and growth areas

- **Review findings not yet addressed:** Code review reported 4 Medium and 4 Low items (e.g. completion notes vs layout changes, test for “blog only on home”, a11y/focus-order test). These were accepted as known debt for now.
- **Single-story epic:** Only one story in Epic 1, so patterns (e.g. velocity, recurring review themes) are from one data point. Harder to generalize “team” patterns.
- **Test gaps called out:** Missing or weak coverage for (1) blog section only on home (not on other routes), (2) explicit a11y/focus-order checks. Worth carrying into Epic 2 as improvement areas.

---

## 5. Key insights and learnings

1. **Shell-first scope worked:** Delivering the blog section as a shell with loading state (no fetch) kept the story small and set a clear contract for Epic 2 (API client + display).
2. **File list discipline:** Review had to correct the story’s file list to include all modified files (e.g. Layout, Home.css, vite.config). Making the “file list” part of the definition of done would reduce rework in future stories.
3. **Documentation vs implementation:** Tension between “completion notes” and “layout changes” in the review suggests clarifying what “completion notes” should cover (e.g. list of behavioral/layout changes, not just high-level summary).
4. **First epic:** No previous retrospective to compare against; this retro establishes the baseline for Epic 2 follow-through.
